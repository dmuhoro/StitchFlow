Because the applied effect was the local migration, the history row was renamed atomically from
`20261106122030` to `20261106160000`:

```sql
update supabase_migrations.schema_migrations
set version = '20261106160000'
where version = '20261106122030'
returning version, name, cardinality(statements);
```

This is the same net effect as `migration repair`, done after comparing the live objects. It is not
a blind "mark reverted" and it did not delete or rewrite an applied migration file.

## Deploy-gate defect found and closed

The first redeploy of this checkpoint shipped `dist/assets/index-BtLeENOW.js`, which embedded
`https://vpathqzkaqdtbykumxeo.supabase.co`. That is the **previous** Supabase project, because the
bundle had been built while `.env.local` still held the old value. The production gate passed anyway:
it checked `process.env.VITE_SUPABASE_URL` (the linked project) but never the project ref inside the
artifact.

Fix: `scripts/ci/verify-build.mjs` now extracts every `https://<ref>.supabase.co` from the bundle and
fails when the ref does not match `VITE_SUPABASE_URL` or the linked `supabase/.temp/project-ref`.
`.github/workflows/ci.yml` adds a negative proof that builds for one ref and runs the production gate
with another; the gate must reject it.

The corrected rebuild (`index-DAH2avX7.js`) embeds `qkhfjlxhulekjrfgrdbz` and passes the production
gate. It is **not published**: Netlify rejects new deploys with
`403 Account credit usage exceeded - new deploys are blocked until credits are added`. The live site
still serves the earlier `index-BtLeENOW.js`, which embeds the retired project
`vpathqzkaqdtbykumxeo`. That mismatch predates this checkpoint — the previous 2026-11-04 deploy
(`index-Bay9DDr9.js`) also embedded the retired project — and it remains a live defect until the
account can publish the corrected artifact.
