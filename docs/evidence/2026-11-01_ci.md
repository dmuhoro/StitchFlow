# 2026-11-01 — Continuous integration gate

## Command / Step

The workflow is `.github/workflows/ci.yml`. It runs on every push and pull request to `main` and has
two required jobs.

### Job 1 — `quality` (Types, docs and bundle)

```bash
npm ci
npm run lint
npm run check:docs
npm run build
npm run verify:build
# then, with VITE_DATA_MODE=supabase and synthetic non-secret values:
npm run build
npm run verify:build
```

### Job 2 — `database` (Migration chain and RLS)

Runs against a `postgres:16` service container:

```bash
npm run verify:db:host
```

### Local proof of the `host` branch of the database job

The runner's database job uses `verify-db.sh host`, which talks to a service container over TCP. That
branch was exercised locally against a `postgres:16` container published on `127.0.0.1:55432`:

```bash
docker run --rm --network host -v "$PWD":/repo -w /repo \
  -e PGHOST=127.0.0.1 -e PGPORT=55432 \
  -e PGUSER=postgres -e PGPASSWORD=postgres -e PGDATABASE=stitchflow_verify \
  postgres:16 bash scripts/verify-db.sh host
```

## Why this gate cannot pass vacuously

- The `database` job replays the chain from an empty database and fails on any SQL error
  (`ON_ERROR_STOP=1`) or failed `ASSERT`. Every RLS scenario raises an exception on violation, so a
  cross-tenant read cannot pass silently.
- The `quality` job asserts build **artifacts**, not source: hashed image assets present, no literal
  source path, no placeholder host or key, no `service_role` marker, and — in supabase mode — the
  runtime guard strings that refuse demo access.
- Both the demo build and the production-mode branch are built, so a change that only works in demo
  mode fails CI.

artifact assertions, and the full database chain with the RLS suite.
